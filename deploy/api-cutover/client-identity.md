# API cutover and client IP identity

Run `python3 -B deploy/api-cutover/test-client-identity.py` from an isolated checkout with its existing `node_modules`, Docker and cached `nginx:1.18` / `node:22-alpine` images. The fixture creates three isolated `--internal` networks, publishes no ports, pulls no images, touches no real users, and deletes its own containers and networks. It uses Express's actual `req.ip` with `trust proxy = 1` and the same anonymous limiter key expression `req.ip || 'anonymous'`. The simulated edge derives the forwarded address from its accepted socket. The test client never sets that header, and the output is boolean results only.

## Reusable route shape and preflight

- Keep both API hostnames on the **same existing ingress Nginx and same upstream identity** in every approved configuration. Under the release lock, the candidate config should change only the two exact upstream targets, from the old loopback socket to the authorised candidate socket. Run `nginx -t` and use graceful reload. Do not add an HTTP relay hop, append to `X-Forwarded-For`, widen Express's trusted hops, or change the currently observed `Host`/`Upgrade`/`Connection` behaviour as part of this switch. Use the same verification in reverse. Retain the old instance and exact original bytes until the inverse and drain have been proven. The fixture's `config()` reproduces this header shape with two private test names.
- The exact health/revision check may contact the candidate's loopback interface directly as an **operational probe**. Do not count that as evidence of a user request's source identity or as proof that no clients can reach it directly. Before an actual switch, the standard release controller needs the precise canonical vhost diff, proof of the expected client key on both hostnames for old and new, and evidence of source admission on both backends at the boundary appropriate to the real topology. Do not add a public endpoint that echoes client addresses.
- A Docker bridge, including `--internal`, blocks unrelated networks but does **not** by itself exclude same-network peers. Before the fixture's transport-peer policy is applied, a legitimate request from an attached peer bypasses Nginx and produces a different key. With the policy, the peer receives 403 at old and new, before cutover, after cutover, and after rollback. This fixture can identify the Nginx container's dedicated private upstream address. At the actual host's existing published loopback port, Docker's bridge gateway is not uniquely Nginx: approving the bridge gateway would also allow other local host callers. For that topology use an independently reviewed ingress-only binding or an enforceable source control. Do not copy the fixture peer predicate to production without proving it uniquely identifies the trusted ingress. Leaving source closure unproven is a deployment blocker, not an acceptance result.

Same limiter key does not demonstrate the same limiter **counter** or shared OTP/OAuth state. These fixture tests do not accept a first production state transition, nor verify actual Cloudflare connectivity, Linux policy, or the real public client IP. Production approval still requires the independently established old→new state ownership and reverse-state proofs.
