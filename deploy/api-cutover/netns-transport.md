# First-migration transport experiment

**Local experiment, not a production release instruction.** `test-netns-transport.py` runs fake HTTP requests in newly owned Docker containers on the Linux VM. It uses the locally verified legacy image as the runtime for both synthetic fixture listeners, not as proof of the legacy application state machine. It leaves host network rules unchanged. Its single disposable helper needs `NET_ADMIN` only in the disposable old container's network namespace, not in the host namespace. No Docker socket, privileged container, or host network is used by the helper. The separately maintained `linux-handoff-qa` harness checks application behavior with the actual old source and candidate on synthetic PostgreSQL.

Run `python3 -B deploy/api-cutover/test-netns-transport.py /absolute/path/to/verified/alpine/apks` with the cached images named by the test. The package directory must match the cached `node:22-alpine` tool image. It is used with networking disabled for dependency installation, and all test queries target only the owned fixture. The temporary bridge is distinct from other networks and mirrors the old API's host loopback port mapping. No test port is published beyond loopback. The fixture cleans its own containers and network, and reports boolean evidence without client addresses.

## What the supported Linux mechanism can do

A candidate can share the old instance's network namespace and listen on a separate port while the old listener and original Docker mappings stay up. A narrow IPv4 NAT rule changes only the destination port for new TCP handshakes arriving on the observed bridge interface. It does not add an HTTP hop or change the forwarded headers or source IP. The fixture keeps the secondary port inaccessible to a direct same-network connection, even after rollback starts. Forward and reverse both retain connection tracking for in-flight requests. Nftables NAT bindings belong to TCP flows, not application operations.

## Why this isn't an ownership switch by itself

- On a connection already established to the old backend, keep-alive can start a **new** authentication operation even after new TCP connections go to the candidate. On reverse cutover, a retained candidate connection similarly continues to reach the candidate. Preserving these sockets and claiming that the old backend cannot receive another stateful request are different guarantees. Closing these sockets immediately to enforce ownership would break the no-disruption requirement.
- The candidate borrows the old container's network endpoint and host port publication. This does not establish a new durable owner for those endpoints or prove they survive retirement of the old container. Traffic entering over another interface, IPv6, or originating in the same namespace must be separately inventoried and tested. The fixture deliberately covers the two existing IPv4 transport paths, not those unverified routes.
- The state admission and its inverse must be proved separately using the real old image. Existing application handoff tests do not prove every packet follows that admission controller. Conversely, network preservation does not copy OTP, limiter windows, or revocation state. Do not put a first migration into service while both processes can independently create the same class of volatile state.

## Keeping legacy as owner during observation

Run the same test with `--observer` to route new connections to an observation ingress rather than to the candidate business process. The initial owner remains legacy. The private ingress sends requests to the existing legacy listener via a distinct loopback source within the same namespace. That dedicated exact tuple is distinguishable from original bridge and host-published connections in both Linux TCP socket tables. In the local fixture, first verify observed successful traffic through both public-shaped paths. The observation start then refuses while any previous direct legacy socket remains live, including a keep-alive that can still initiate an application request. Only after the test witnesses the original requests complete and their sockets close naturally may it invoke the actual `trackFamily.startObservation()`. An existing ingress-owned upstream keep-alive is still present at that point, demonstrating it was distinguished, not mistaken for a direct connection. The first-hour timer is never advanced in the fixture, and business ownership does not transfer.

The inverse invalidates the observation clock **before** restoring new direct connections. Existing observed connections finish on the ingress, new requests again reach legacy directly, and the old instance stays running. An old socket disappearing does not prove a disconnected client's queued mutation or deferred side effect completed. In production the timer must remain fail-closed unless the actual legacy implementation or existing authoritative observations prove completion for that case. The local fixture uses successful final responses followed by graceful closes and does not cover that gap. A production observer also needs real peer/source authority and full HTTP, authentication, and streaming compatibility, not the test-only forwarding handler. The ingress-only tuple must remain exclusive and the complete source path inventory must be validated before relying on the gate.

## Namespace-local output and restart

`test-netns-restart.py /absolute/path/to/verified/alpine/apks` adds the missing narrow IPv4 OUTPUT and Docker lifecycle checks. It changes no host firewall rule. The same namespace's new TCP flows to a *local* address on the old port are redirected to the observation ingress. Only the observer-specific 127.0.0.2 to 127.0.0.1 pair is exempt. The local-destination match matters because the namespace must not capture traffic to another service on the same port. This proof does not make a loopback source intrinsically exclusive. An installed role must be verified and reserved by the managed ingress.

Do not enable shared ownership while the old Docker instance can autorestart. A crash can recreate its network namespace but reuse its published host port while the old netfilter sidecar remains in the abandoned namespace. The app then accepts a fresh legacy request outside the proxy even though the durable owner already says shared. Changing just this test service's policy to `no` before an application failure keeps the published API closed while preserving the owner record. A restart policy does not constrain an explicit Docker start, Compose recreate, or other reconcile service.

The API's existing manager must also exclusively own explicit starts and recreates. Before an ownership transfer, record an exact, read-back `no` policy for the pinned old container and reconcile the declared policy so a normal API-only operation cannot restore it. The recovery action must start with the service ingress closed, read persisted owners rather than initialize new state, verify the target namespace and complete rules, prove legacy is reachable only through the dedicated provenance, and verify all shared families use compatible state and rollback artifacts. Only then allow API traffic on that generation. On ambiguity, leave the API closed rather than starting the bare old application on a fresh namespace. This procedure does not require stopping the frontend, PostgreSQL, or Nginx, but API availability during recovery is not preserved by disabling restart alone. No supported production supervisor or IPv6/all-interface topology proof is supplied by this fixture.

Two additional local checks are independent of the IPv4 transport replay:

- `test-netns-ipv6.py` uses a disposable network namespace and the actual proxy with an IPv6-loopback-only listener. A narrow IPv6 OUTPUT rule redirects new `::1:3000` connections. A real Express target observes exactly `req.ip === '::1'` before and after. Existing keepalive remains on its original path until it closes, and the inverse restores fresh direct connections. The upstream still uses its IPv4 dedicated route. This proves the IPv6 mechanism, not its installation in the current production observer.
- `test-managed-api-recovery.py` exercises the actual Docker Compose API-only force-recreate command against synthetic HTTP in the pinned local legacy and recovery images. While legacy owns state, new connections pause and a held response completes before recreation. API remains closed until current namespace rules and startup evidence are restored. A shared owner blocks normal force-recreate with the old image but admits the compatible recovery image with fresh evidence. The fixture confirms DB/web container identities and start times did not change. This is a supervisor contract proof, not an actual app recovery or an authoritative production owner receipt.

## Lower-change route to revisit

The reviewed formal configuration and short connection observations identified no actual straight-to-origin customer dependency. They do **not** prove a closed source set. Before treating direct access as discardable, identify and reconcile the owners of host-loopback and bridge calls with independently trustworthy observation, and establish which operational direct probes are strictly read-only. Move verified active callers through the existing trusted ingress with an explicit positive test for each caller and its limiter identity, then verify no state-producing requests can still reach the old owner outside that path in either direction. This keeps current access functional while avoiding a new privileged network dependency. Until that closure is proved, neither denying all direct traffic nor the transport-only experiment is a production-safe fix.
